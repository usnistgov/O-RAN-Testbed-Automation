# OCUDU and srsRAN_4G ZMQ Interoperability Fixes

## Summary

When the testbed runs OCUDU gNB with srsRAN_4G UE over the ZMQ radio backend inside Ubuntu VirtualBox guests, startup and attach can stall before the system reaches a usable data session. The observed failures reproduce on Ubuntu 20.04, 22.04, and 24.04 VirtualBox VMs. The same failures have not yet been characterized on bare-metal hosts.

The changes in this patch set address three externally visible failures:

- OCUDU gNB starts but does not reliably reach the `==== gNB started ===` banner.
- srsUE reaches `RRC Connected` but does not reliably complete PDU session establishment.
- Multi-UE ZMQ-broker operation can overload the emulated RF path in VirtualBox when the single-UE 20 MHz profile is reused unchanged.

## Observed Impact

The failure prevents automated interoperability testing because the gNB or UE can remain alive while forward progress has stopped. In the UE case, random access and RRC setup may complete, but NAS/PDU-session procedures do not complete. The result is a testbed that appears partially running but cannot carry user-plane traffic.

## Change Classification

The patch set contains three categories of changes:

- Build portability fixes: YAML target visibility, SCTP event guards, and the `M_PI_2f` replacement. These are not attach fixes, but they keep the same OCUDU revision buildable across the tested Ubuntu environments.
- Runtime progress fixes: MAC/RLC executor changes, temporary C-RNTI handling, PRACH offset handling, and the CU-UP closed-connection guard. These are directly related to gNB startup or UE attach progress.
- ZMQ timing fixes: ZMQ receive timeout handling and current-slot fallback scheduling. These are the most environment-sensitive changes and are most relevant to ZMQ radio operation in virtualized deployments.

## OCUDU Changes

Several OCUDU procedures synchronously dispatched work to executors that can already be blocked by the same attach/startup path. Under the ZMQ timing observed in VirtualBox, this can create a progress dependency where the slot-processing path is waiting for work that cannot run. The MAC and RLC changes remove those self-wait patterns for cell activation, UE creation, bearer configuration, and RLC buffer/status notifications.

The ZMQ receive change allows the receiver to return zero samples after the link has already seen non-zero samples and a receive timeout expires. This keeps the PHY time source advancing through silent intervals instead of treating an unanswered request as a hard stall. This change is limited to the ZMQ radio backend.

The fallback scheduler change keeps SRB0/contention-resolution downlink scheduling in the current slot. This avoids a random-access timing gap seen with the ZMQ/srsUE path.

The CU-UP connection-manager change adds a missing return after a closed E1 connection is detected. This is defensive and prevents forwarding a message through a closed connection.

## Testbed Configuration Changes

The direct ZMQ path and the ZMQ-broker path now use separate generated RF profiles. Direct single-UE ZMQ keeps the 20 MHz / 23.04 Msps profile used by the original testbed. When `USE_ZMQ_BROKER=true`, the generator selects the OCUDU multi-UE tutorial profile: 10 MHz channel bandwidth, 11.52 Msps gNB and UE sample rates, CORESET0 index 6, 64 contention-based PRACH preambles, and the OCUDU narrow-band PUCCH/SR resource profile for 5/10 MHz cells. OCUDU commit `3f609dea0e` does not accept `cell_cfg.dl_ssb_arfcn`; the UE configuration generator derives the matching Band 3 SSB ARFCN locally. The generated GNU Radio broker is synchronized to the same sample rate, runs with a real-time slow-down ratio of 1, and starts with zero path loss for each UE so attach validation is deterministic; path loss can still be changed from the broker UI.

Broker mode also increases the gNB PDU-session request timeout from the direct-mode default of 3 seconds to 30 seconds. This avoids releasing a UE while NAS/PDU-session setup is still making progress in slower VirtualBox guests.

The broker Python runtime script is generated by `generate_zmq_broker.sh` from the requested UE list instead of compiled from the static tutorial `.grc` asset. Each requested UE receives matching downlink and uplink ZMQ branches using the testbed namespace address scheme. This keeps the default three-UE tutorial scenario intact while allowing larger UE sets to be configured without hand-editing the broker flowgraph, subject to host CPU capacity and subscriber registration.

The top-level runtime starts all broker-mode srsUE instances before enforcing PDU-session checks. This matches the generated GNU Radio graph, where the uplink combiner has one input branch per requested UE. The gNodeB runtime also waits for the broker REP sockets to listen before starting OCUDU, avoiding early VirtualBox runs where the broker process exists but the simulated RF endpoints are not ready.

The top-level configuration path runs a broker/config consistency verifier after gNB and UE configuration generation. The verifier checks that the generated broker UE list, namespace IP addresses, ZMQ ports, gNB sample rate, and UE sample rates agree before the testbed is launched.

After a live run, `User_Equipment/install_scripts/get_pdu_sessions.sh` can be used to list the PDU-session addresses found in the recorded UE stdout files. This provides a concrete check for the broker-mode success condition before reporting the VirtualBox result.

This keeps the source patches general while avoiding broker-only VirtualBox failure modes where three srsUE instances and GNU Radio inherit the heavier single-UE 20 MHz profile, or where 10 MHz cells are generated without enough narrow-band PUCCH/SR resources for the early UE attach path.

## srsRAN_4G Changes

The srsUE changes correct temporary C-RNTI handling during random access:

- MAC reports the temporary C-RNTI as `srsran_rnti_type_tc`.
- PHY searches the RA search space for temporary C-RNTI contention-resolution DCI.
- PHY schedules ACK feedback for downlink grants sent with temporary C-RNTI.

The NR RACH configuration also now applies the 3GPP default of 64 contention-based RA preambles when `totalNumberOfRA-Preambles` is absent, and preserves the same value when OCUDU encodes it through `ssb-perRACH-OccasionAndCB-PreamblesPerSSB`. The RA procedure applies the same fallback before selecting a preamble. The random preamble draw uses the valid inclusive range `0..nof_preambles-1`, and the RA RNG seed includes the process ID as well as wall-clock time. Without these defaults, the UE MAC could treat the preamble count as zero and repeatedly select preamble 0; without a per-process seed component, simultaneous UE starts in a VM can still share the same random stream.

The PRACH offset change computes a valid temporary PRACH frequency offset before SIB1 provides the final PRACH configuration. The RF ZMQ parsing change fixes `log_trx_timeout` parsing so the intended option is read from the correct temporary buffer.

The NR Scheduling Request path now accepts a nonzero `sr-ProhibitTimer` from the gNB configuration instead of rejecting the SR configuration as unsupported. The UE MAC tracks the prohibit timer between SR opportunities, suppresses SR attempts while it is running, and resumes SR transmission after expiry. Additional UE stdout diagnostics identify the decoded SR configuration, the assigned PUCCH SR resource, SR opportunities, PUCCH UCI transmissions, and any received PUSCH grants. These diagnostics are used to distinguish a missing SR resource from a transmitted SR that does not lead to an uplink grant.

## Portability and Risk

The build-portability patches are expected to be low risk across Ubuntu releases because they address compiler/header/CMake compatibility issues.

The runtime patches are most relevant to ZMQ-based deployments. Traditional OCUDU deployments using hardware RF frontends should not exercise the ZMQ receive path. The scheduler fallback change is not ZMQ-specific in code, but it affects only fallback SRB0/SRB1 scheduling during random access and early UE setup; it should not affect steady-state user-plane scheduling after the UE leaves fallback operation.

The primary open risk is whether all runtime changes are required on bare-metal hosts. Current reproducibility evidence is strongest for Ubuntu VirtualBox VMs. If maintainers prefer a narrower upstream change, the ZMQ receive and fallback-scheduler changes should be reviewed as the most environment-sensitive parts.

## Reproduction

Known reproduction environment:

- Host virtualization: VirtualBox
- Guest operating systems tested: Ubuntu 20.04, Ubuntu 22.04, Ubuntu 24.04
- Radio backend: ZMQ direct or ZMQ broker
- gNB: OCUDU
- UE: srsRAN_4G srsUE

Reproduction steps:

1. Apply the testbed patches.
2. Build OCUDU gNB and srsRAN_4G srsUE.
3. Start the full testbed with the top-level `run.sh`.
4. Observe whether the gNB reaches `==== gNB started ===`.
5. Observe whether the UE reaches `RRC Connected`, `PDU Session Establishment successful`, and `RRC NR reconfiguration successful`.
6. If attach stops after `RRC Connected`, inspect the UE stdout for `RRC NR SR config`, `RRC NR PUCCH SR resource`, `SR: signalling`, `NR UL PUCCH UCI`, and `NR UL PUSCH grant` lines.
7. With `USE_ZMQ_BROKER=true`, verify the generated gNB and UE configs use 10 MHz / 11.52 Msps, include the narrow-band PUCCH/SR profile, and that UE1, UE2, and UE3 each complete PDU-session establishment.
8. After stopping the run, execute `User_Equipment/install_scripts/get_pdu_sessions.sh 1`, `User_Equipment/install_scripts/get_pdu_sessions.sh 2`, and `User_Equipment/install_scripts/get_pdu_sessions.sh 3` from the repository root to validate the captured UE logs.

Before these changes, the system can stall before the gNB startup banner, after UE `RRC Connected`, or during broker-based multi-UE attach. A successful broker-mode validation requires each configured UE to reach PDU session establishment in the same live run.

## Validation

The expected successful output includes:

```text
==== gNB started ===
RRC Connected
PDU Session Establishment successful. IP: 10.45.0.101
RRC NR reconfiguration successful.
```
